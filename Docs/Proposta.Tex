\begin{abstract}
O presente documento detalha a arquitetura e implementação de um sistema colaborativo em tempo real para Gestão de Equipas e Tarefas. Desenvolvida no âmbito da unidade curricular de Paradigmas Emergentes para o Desenvolvimento Web e Mobile, a solução integra uma aplicação \textit{frontend} em Flutter e um \textit{backend} em C\# .NET. A arquitetura baseia-se no paradigma \textit{Clean Architecture}, garantindo uma separação rigorosa de responsabilidades. A comunicação serão feitas atraves de GraphQL para operações transacionais e métricas complexas, e WebSockets para reatividade em tempo real. A adoção de padrões de desenho avançados, como CQRS, Builder (com CRTP), Factory e Strategy, reflete o alinhamento total com os objetivos de avaliação estipulados.
\end{abstract}

\section{Arquitetura do Sistema: Clean Architecture}
O projeto foi estruturado em quatro camadas independentes, promovendo o encapsulamento, a testabilidade e a escalabilidade do sistema:

\begin{itemize}
    \item \textbf{Domain Layer (Core):} O coração do sistema. Contém as regras de negócio puras e as entidades principais (como Utilizadores, Projetos e Tarefas). É aqui que se centralizam os mecanismos estruturais para garantir que os dados assumem sempre um estado válido e seguro na sua instanciação, recorrendo a \textit{Builders} tipados com CRTP para assegurar a reutilização de código e o estrito cumprimento do princípio DRY.
    \item \textbf{Application Layer:} Responsável pela orquestração dos casos de uso através do padrão CQRS. Define \textit{Commands} e \textit{Handlers}, as \textit{Factories} polimórficas e o contrato das estratégias de notificação. Define também as interfaces dos repositórios.
\item \textbf{Infrastructure Layer:} É a camada encarregue de lidar com os detalhes físicos e de infraestrutura. Para a persistência de dados, utiliza o \textbf{Entity Framework Core (EF Core)} como ORM (\textit{Object-Relational Mapper}), garantindo a tradução fluida e segura das entidades de domínio para a base de dados relacional. É também nesta camada que residem os repositórios concretos e os serviços de entrega de mensagens (como os \textit{WebSockets}).
    \item \textbf{Presentation Layer:} Expõe a API GraphQL. Gere a receção de pedidos transcrevendo os \textit{Input DTOs} em \textit{Commands} (via Mapster), e expõe as subscrições de WebSockets para o cliente Flutter.
\end{itemize}

\section{Objetivos do Projeto}
O objetivo central deste projeto consiste na conceção e desenvolvimento de um sistema colaborativo, a operar em tempo real, dedicado à gestão integrada de projetos, acompanhamento de tarefas e reporte detalhado de horas de trabalho.

A solução foi desenhada para dar resposta às necessidades operacionais e de sincronização de equipas, focando-se nas seguintes vertentes funcionais:

\begin{itemize}
    \item \textbf{Gestão de Projetos e Tarefas:} Permitir a criação, organização e monitorização do estado de vários projetos e das respetivas tarefas, garantindo uma visão clara sobre a que atividades cada membro da equipa está atribuído.
    
    \item \textbf{Reporte de Horas (Timesheets):} Facilitar o registo rigoroso do tempo investido pelos utilizadores nas diferentes tarefas e categorias de projeto, permitindo cruzar as horas reportadas com o orçamento de tempo (\textit{budget}) estipulado.
    
    \item \textbf{Presença e Colaboração em Tempo Real:} Proporcionar um ambiente interativo onde é possível identificar, de forma instantânea, o contexto de cada membro da equipa. O sistema permite distinguir em tempo real se um utilizador está ativamente a reportar horas numa tarefa específica ou se está apenas a visualizar os detalhes de um projeto naquele momento.
    
    \item \textbf{Monitorização de Esforço e Atribuições:} Oferecer à equipa e aos gestores uma visão global sobre a distribuição do trabalho, permitindo saber exatamente onde (em que tarefas) as horas estão a ser gastas, por quem foram reportadas e qual a taxa de progresso das atividades atribuídas.
\end{itemize}

\section{Modelo de Entidades e Domínio}
O modelo de dados foi desenhado para representar os requisitos de negócio, para garantirmos a integridade relacional da informação. A arquitetura assenta nas seguintes entidades e relações principais:

\begin{itemize}
    \item \textbf{Estrutura Organizacional (User e Team):} Os utilizadores (\textit{Users}) assumem papéis específicos (\textit{Roles}) e encontram-se agrupados em equipas (\textit{Teams}). 
    
    \item \textbf{Núcleo de Gestão (Project):} Atua como a entidade agregadora do trabalho. Cada projeto possui um orçamento de horas (\textit{BudgetHours}), periodos temporais (\textit{StartDate} e \textit{EndDate}), é gerido por um responsável (\textit{Manager}) e encontra-se atribuído a uma equipa.
    
    \item \textbf{Polimorfismo de Tarefas (FeatureTask e BugTask):} A modelação reflete a natureza distinta das atividades de engenharia. As tarefas associam-se a projetos, mas dividem-se logicamente em: novas funcionalidades (\textit{FeatureTasks}, estimadas através de \textit{Story Points}) e correções de anomalias (\textit{BugTasks}, que exigem o registo da severidade e do ambiente afetado).
    
    \item \textbf{Sistema de Alertas (Notification):} Entidade dedicada ao registo persistente de eventos e mensagens direcionadas aos utilizadores, para servir de histórico para as notificações em tempo real ou email.
\end{itemize}

\section{Justificação dos Padrões de Desenho Aplicados}
A solução implementa múltiplos \textit{Design Patterns} para resolver problemas estruturais complexos, garantindo que o sistema se mantém eficiente, coeso e altamente escalável:

\begin{itemize}
    \item \textbf{Builder Pattern com CRTP (Domain Layer):} Utilizado para evitar construtores complexos com múltiplos parâmetros e garantir as regras de negócio durante a criação de objetos. A adoção do padrão CRTP (\textit{Curiously Recurring Template Pattern}) permitiu partilhar a lógica de construção entre diferentes tipos de entidades de tempo e tarefas, eliminando a duplicação de código de forma fluente.
    
    \item \textbf{Factory Pattern (Application Layer):} Atua como o motor central de decisão polimórfica. Ao receber um pedido do exterior, a fábrica avalia o tipo de entidade pretendida e invoca o \textit{Builder} correspondente de forma automática. Isto liberta a interface de utilizador e a API de conterem lógicas condicionais complexas.
    
    \item \textbf{Strategy Pattern (Infrastructure/Application):} Aplicado ao sistema de envio de notificações. Permite que a aplicação de enviar notificações por, comunicação em tempo real via WebSockets ou envio de e-mail.
    
    \item \textbf{Singleton Pattern (Infrastructure / Cross-Cutting):} Utilizado para a gestão centralizada do registo de eventos do sistema (\textit{Logs}). Garante a existência de uma instância única global, o que previne conflitos e condições de corrida no acesso aos ficheiros de registo, minimizando também o consumo de memória durante a execução.
    
    \item \textbf{CQRS (Command Query Responsibility Segregation):} Adotado para separar explicitamente as operações de escrita e alteração de estado das operações exclusivas de leitura de dados. Esta divisão otimiza o desempenho das consultas para os \textit{dashboards} e espelha perfeitamente a natureza bidirecional da API GraphQL.
\end{itemize}

\section{Tecnologias Core e Integração}
O sistema foi concebido em torno das duas tecnologias exigidas:

\subsection{GraphQL (Data Operations \& Mapping)}
Utilizado para expor uma API estritamente tipada, cuja implementação no \textit{backend} .NET é suportada pela \textit{framework} \textbf{HotChocolate}. O cliente Flutter submete \textit{Input DTOs}, que são automaticamente mapeados para \textit{Commands} internos ao utilizar a biblioteca \textbf{Mapster}. O \textit{backend} processa estas \textit{mutations} de forma polimórfica e devolve \textit{Output DTOs} desenhados à medida das necessidades da Interface de Utilizador (UI).

\subsection{WebSockets (Real-Time Communication)}
Empregues para assegurar o contexto colaborativo exigido num sistema de gestão de equipas. A \texttt{WebSocketDeliveryStrategy} garante que alterações de estado nas tarefas e alertas de presença sejam refletidos nos quadros virtuais de todos os elementos da equipa de forma instantânea.
